# 解釋 Git 中的 Rebase 和 Merge 的區別

在 Git 版本控制系統中，`rebase` 和 `merge` 是兩種整合來自不同分支的變更到一個分支的方法。雖然它們的目標相同，但是實現方式和結果有所不同。理解這兩者的區別對於開發者在使用 Git 進行版本控制時非常重要。

## Merge（合併）

Merge 是將兩個分支的歷史合併到一起的過程。當你執行一次 merge 操作時，Git 會創建一個特殊的 commit—稱為 "merge commit"（合併提交）—來表示兩個分支的歷史已經合併。如果在合併過程中存在任何衝突，Git 會提示用戶手動解決這些衝突後再完成合併操作。

**優點**：
- 保留了完整的分支歷史和順序。
- 合併操作是非破壞性的，即原始分支的歷史保持不變。

**缺點**：
- 可能會產生複雜的歷史圖譜，尤其是在頻繁合併的項目中。

### 示例

假設從 `main` 分支創建一個新分支 `feature`：

```bash
git checkout -b feature main
```

在 `feature` 分支上開發完成後，你想將這些變更合併回 `main` 分支：

```bash
git checkout main
git merge feature
```

## Rebase（變基）

Rebase 是將一系列提交按照原有順序應用到另一個基底上面的過程。與 merge 不同，rebase 在整合分支時會創建一系列新的提交而不是產生一個 merge commit。這樣做的目標是為了保持項目歷史的線性。

**優點**：
- 產生乾淨、線性的提交歷史。
- 可以避免不必要的 merge commit。

**缺點**：
- 可能會改變提交歷史。
- 如果不當使用，可能會導致版本歷史混亂。

### 示例

假設你正在 `feature` 分支上開發，並希望將最新的 `main` 分支變更整合到你的 `feature` 分支：

```bash
git checkout feature
git rebase main
```

這樣做會將 `feature` 分支上開發完成後還未推送到遠端仓庫中提交重新應用到 `main` 分支最新的提交之上。

## 常見問題處理

### 衝突解決

無論是在執行 merge 還是 rebase 操作時，都有可能遇到衝突。處理步驟基本相同：

1. 打開衝突文件，找到並解決所有衝突部分。
2. 使用 `git add .` 將解決後的文件標記為已解決。
3. 如果是 rebase 操作，使用 `git rebase --continue` 繼續；如果是 merge 操作，則使用 `git commit` 完成合併。

### 注意事項

1. **不要** 在公共或共享分支上使用 `rebase` 操作，因為它會改變歷史。
2. 在執行 rebase 或 merge 前，確保當前工作目錄是乾淨的（沒有未提交或未推送的更改）。

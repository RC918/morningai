# 技術債 Sprint 流程

本文件說明如何系統性地管理和處理技術債，確保專案長期健康發展。

## 背景

技術債是軟體開發過程中累積的「欠款」，包括：

- 為了快速交付而採取的捷徑
- 過時的依賴和架構
- 缺少的測試和文件
- PR review 過程中識別但延後處理的改進項目

如果不定期處理，技術債會導致開發速度下降、bug 增加、維護成本上升。

## 技術債分類

### 按優先級分類

| 優先級 | 定義 | 處理時間 | 範例 |
|-------|------|---------|------|
| P0-urgent | 阻擋性問題 | 立即處理 | 安全漏洞、production crash |
| P1 | 重要但非阻擋 | 1-2 週內 | 效能問題、重要重構 |
| P2 | 改進項目 | 2-4 週內 | 程式碼優化、測試補充 |
| P3 | Nice to have | 視情況 | 文件更新、小型重構 |

### 按類型分類

| 類型 | 說明 | 範例 |
|------|------|------|
| 架構債 | 系統設計層面的問題 | 模組耦合過高、缺少抽象層 |
| 程式碼債 | 程式碼品質問題 | 重複程式碼、命名不清 |
| 測試債 | 測試覆蓋不足 | 缺少 unit tests、edge cases |
| 文件債 | 文件缺失或過時 | API 文件、架構說明 |
| 依賴債 | 依賴版本過舊 | 安全更新、breaking changes |

## 每週技術債 Sprint

### 時間安排

建議每週固定安排 2-4 小時處理技術債：

| 時段 | 活動 | 時長 |
|------|------|------|
| 週一 | 技術債 Review Meeting | 30 分鐘 |
| 週一-週四 | 技術債處理時間 | 2-3 小時 |
| 週五 | 進度更新和下週規劃 | 30 分鐘 |

### 週一：技術債 Review Meeting

**目的**：審視現有技術債，決定本週處理項目

**議程**：
1. 回顧上週完成的技術債項目（5 分鐘）
2. 審視新增的技術債 issues（10 分鐘）
3. 決定本週處理的項目（10 分鐘）
4. 分配負責人（5 分鐘）

**輸出**：
- 本週技術債處理清單
- 每個項目的負責人和預估時間

### 技術債處理流程

#### 1. 識別技術債

技術債來源：
- PR review 過程中的 [Parking Lot](./FOLLOWUP_PARKING_LOT.md) 項目
- Code review 發現的問題
- 開發過程中的 TODO 註解
- 效能監控發現的瓶頸
- 安全掃描報告

#### 2. 建立 Issue

使用以下模板建立技術債 issue：

```markdown
## 標題
[Tech Debt] 簡短描述問題

## 類型
- [ ] 架構債
- [ ] 程式碼債
- [ ] 測試債
- [ ] 文件債
- [ ] 依賴債

## 優先級
P2 - 改進項目

## 問題描述
詳細說明技術債的內容和影響。

## 建議解決方案
1. 步驟一
2. 步驟二

## 預估工作量
- 時間：2-4 小時
- 複雜度：中

## 相關連結
- 原始 PR: #1234
- 相關 issue: #5678
```

#### 3. 優先級排序

使用以下矩陣決定優先級：

```
        影響範圍
        低      高
      +-------+-------+
修復  | P3    | P2    |
難度  +-------+-------+
高    | P3    | P1    |
      +-------+-------+
低
```

> **注意**：低影響項目無論難度高低都是 P3，因為不應佔用 Sprint 時間。

#### 4. 處理和驗證

1. 建立 PR 處理技術債
2. 在 PR description 中引用原始 issue
3. 確保測試通過
4. 請求 code review
5. 合併後關閉相關 issue

## 技術債追蹤

### GitHub Labels

使用以下 labels 追蹤技術債：

| Label | 說明 |
|-------|------|
| `tech-debt` | 所有技術債 issues |
| `P0-urgent` | 緊急技術債 |
| `P1` | 重要技術債 |
| `P2` | 一般技術債 |
| `P3` | 低優先級技術債 |
| `architecture` | 架構相關 |
| `testing` | 測試相關 |
| `documentation` | 文件相關 |

### 追蹤指標

定期追蹤以下指標：

| 指標 | 目標 | 說明 |
|------|------|------|
| 技術債 issue 數量 | 持續下降 | 總數應逐漸減少 |
| P1 issue 平均處理時間 | < 2 週 | 重要問題應快速解決 |
| 每週處理數量 | 3-5 個 | 維持穩定的處理速度 |
| 新增 vs 關閉比例 | < 1 | 關閉應多於新增 |

## 最佳實踐

### Do's

- 定期安排時間處理技術債
- 在 PR review 時識別並記錄技術債
- 使用 [Parking Lot](./FOLLOWUP_PARKING_LOT.md) 機制避免 scope creep
- 優先處理影響開發效率的技術債
- 將大型技術債拆分為小型可管理的任務

### Don'ts

- 不要讓技術債無限累積
- 不要在功能開發 PR 中混入大量重構
- 不要忽略安全相關的技術債
- 不要只處理簡單的技術債而忽略重要的

### Problem Statement

In the past, Sentry error logs indicated that certain operations held PostgreSQL connections for approximately 2 minutes during workflow execution. This behavior led to performance bottlenecks and affected the overall reliability of the platform.

### Root Cause Analysis

Upon investigation, it was discovered that the connection handling mechanism was not optimized for per-operation usage. Instead, connections were being borrowed at the start of a workflow and held until completion, irrespective of whether database interaction was ongoing. This approach unnecessarily tied up resources.

### Fix Description

The implemented fix involves a shift to a per-operation connection borrowing strategy. Now, connections are acquired from the pool immediately before a database operation and released back to the pool once the operation is completed. This change ensures connections are only held when necessary, improving resource utilization and system performance.

```python
# Example of per-operation connection handling
with get_db_connection() as conn:
    perform_database_operation(conn)
```

In this pseudo-code example, `get_db_connection` is a context manager that handles borrowing a connection from the pool before an operation and returning it afterward.

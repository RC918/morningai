# Fixing Rate Limit Counter Leak in MorningAI

## Summary

This FAQ addresses a critical bug fix related to the rate limit functions within the MorningAI platform. The issue was identified in three specific functions that are instrumental in managing webhook events and their processing rates. The affected functions are:
- `check_pr_rate_limit()`
- `check_deepwiki_rate_limit()`
- `check_notification_rate_limit()`

The root cause of the bug was traced back to the sequence of operations within these functions. Initially, they incremented the counter using `INCR` before evaluating if the operation exceeded the predefined rate limits. Consequently, even when the function determined that the rate limit was breached (`returning False`), the counter had already been incremented. This faulty logic led to an unintended accumulation of count values upon each retry, significantly observed in production environments where counts surged unexpectedly from 18 to 28.

### Code Example

Before the fix, a typical rate limit function might have looked like this:

```python
def check_pr_rate_limit():
    # Increment first, then check
    current_count = redis.incr('pr_rate_limit_counter')
    if current_count > MAX_LIMIT:
        return False
    return True
```

The corrected approach involves checking the current count before incrementing:

```python
def check_pr_rate_limit():
    current_count = redis.get('pr_rate_limit_counter')
    if int(current_count) >= MAX_LIMIT:
        return False
    # Only increment if under the limit
    redis.incr('pr_rate_limit_counter')
    return True
```

### Implementation Details

The fix was implemented across all three affected functions within the MorningAI platform's codebase. This adjustment ensures that the counter for rate limits is only incremented following a successful check against the maximum threshold, thereby preventing any unnecessary leaks or accumulation of counter values.

### Common Troubleshooting Tips

- **Counter Mismatches**: If you observe discrepancies in expected vs actual counter values, ensure that any rate-limiting logic follows the correct sequence of check-then-increment.
- **Rate Limit Breaches**: Unexpectedly hitting rate limits may indicate an issue with how counters are managed or reset. Verify that counters are appropriately reset after reaching their max limit or within expected intervals.
- **Performance Impact**: Check for any performance degradation that might be tied to frequent access or modifications of counter values in storage. Optimize by batching operations or reviewing your rate limiting thresholds and logic.

# UX Ops Pipeline Documentation

## Overview

The UX Ops Pipeline is a comprehensive CI/CD integration that enforces design system consistency, accessibility standards, internationalization coverage, and performance benchmarks across all frontend applications.

This pipeline implements a multi-phase approach with **Warning Mode** for data collection before enabling blocking enforcement.

## Architecture

### Pipeline Phases

1. **Phase 1**: Design Tokens Drift Check (BLOCKING)
2. **Phase 2**: AI Perceptual QA (WARNING MODE)
3. **Phase 3**: Objective UX Metrics (WARNING MODE) ← Current Phase

### Workflow Jobs

```yaml
jobs:
  smoke-tests          # Fast validation (BLOCKING)
  tokens-drift-check   # Design tokens consistency (BLOCKING)
  visual-regression-test  # VRT baseline comparison (WARNING)
  motion-performance-test # Animation performance (WARNING)
  accessibility-audit  # A11y violations (WARNING)
  i18n-coverage       # Translation coverage (WARNING)
  ai-perceptual-qa    # AI-powered UX analysis (WARNING)
  ux-quality-gate     # Final summary and decision
```

## Phase 1: Design Tokens Drift Check (BLOCKING)

**Status**: Blocking Mode (Enforced)  
**Implementation**: PR #1173  
**Tracking**: Issue #1187

### Overview

The Design Tokens Drift Check ensures consistency between the centralized design tokens in `@morningai/shared-ui` and the application-specific implementations. This prevents design system fragmentation and maintains a single source of truth.

### Architecture

**Centralized Tokens**: `packages/shared-ui/src/design-tokens.ts`
- Single source of truth for all design tokens
- Exported via `@morningai/shared-ui` package
- Used by frontend-dashboard and owner-console

**Token Categories**:
- Colors (primary, accent, semantic)
- Spacing (xs, sm, md, lg, xl, 2xl, 3xl)
- Typography (font families, sizes, weights, line heights)
- Radius (border radius values)
- Shadow (box shadow definitions)
- Animation (durations, easing functions)
- Accessibility (WCAG AAA colors, focus styles, touch targets)

### Design Token Change Process

#### 1. Adding New Tokens

**Step 1**: Update source tokens
```bash
# Edit the token definition
vim packages/shared-ui/src/tokens.json
```

**Step 2**: Verify token generation
```bash
cd packages/shared-ui
pnpm run build
# Verify dist/tokens.css contains new variables
```

**Step 3**: Run unit tests
```bash
cd packages/shared-ui
pnpm test
# Ensure all 31+ tests pass
```

**Step 4**: Update consuming applications
```typescript
// In frontend-dashboard or owner-console
import { getToken, applyDesignTokens } from '@morningai/shared-ui'

// Access new token
const newColor = getToken('color.accent.blue.500')

// Or apply all tokens to DOM
applyDesignTokens() // Applies to document.documentElement
```

**Step 5**: Run drift check locally
```bash
# From repo root
node scripts/check-tokens-drift.mjs
```

**Step 6**: Create PR and verify CI passes
- Drift check runs automatically in CI
- All checks must pass before merge

#### 2. Modifying Existing Tokens

**⚠️ Breaking Change Warning**: Modifying token values affects all consuming applications.

**Process**:
1. Update `tokens.json` with new values
2. Run unit tests to verify no regressions
3. Run VRT to detect visual changes: `pnpm run test:vrt`
4. Update VRT baselines if changes are intentional
5. Document breaking changes in PR description
6. Notify team before merging

**Example**:
```json
// Before
"primary": {
  "500": "#0ea5e9"
}

// After (breaking change)
"primary": {
  "500": "#0284c7"  // Darker shade
}
```

#### 3. Deprecating Tokens

**Process**:
1. Mark token as deprecated in comments
2. Add migration guide in PR description
3. Update all consuming applications in same PR
4. Remove deprecated token after migration complete

**Example**:
```typescript
// tokens.json
{
  "color": {
    "legacy-blue": "#0ea5e9",  // @deprecated Use color.primary.500 instead
    "primary": {
      "500": "#0ea5e9"
    }
  }
}
```

### Drift Check Governance

#### What is Drift?

**Drift** occurs when application-specific token implementations diverge from the centralized design tokens, causing:
- Visual inconsistencies across applications
- Maintenance burden (multiple sources of truth)
- Design system fragmentation

#### Drift Detection

The drift check script (`scripts/check-tokens-drift.mjs`) validates:

1. **Token Import Consistency**
   - All apps must import from `@morningai/shared-ui`
   - No local token definitions allowed

2. **CSS Variable Usage**
   - Apps should use CSS variables generated by `getCSSVariables()`
   - No hardcoded color/spacing values in components

3. **Token Access Patterns**
   - Use `getToken()` for programmatic access
   - Use `applyDesignTokens()` for DOM injection
   - No direct imports from `tokens.json`

#### Enforcement

**CI/CD Integration**:
```yaml
# .github/workflows/frontend.yml
- name: Check design tokens drift
  run: node scripts/check-tokens-drift.mjs
  # This check is BLOCKING - PR cannot merge if drift detected
```

**Local Development**:
```bash
# Run before committing
node scripts/check-tokens-drift.mjs

# Expected output (success):
✅ No design token drift detected
✅ All applications use centralized tokens from @morningai/shared-ui
```

**Failure Example**:
```bash
❌ Design token drift detected!

Issues found:
1. frontend-dashboard/src/styles/custom.css
   - Hardcoded color: #0ea5e9 (should use var(--color-primary-500))

2. owner-console/src/components/Button.tsx
   - Direct token import (should use getToken() from @morningai/shared-ui)

Please fix these issues before merging.
```

#### Exemptions

Some files are exempt from drift checks:
- `final-override.css` (intentional overrides)
- Test files (`*.test.ts`, `*.spec.ts`)
- Storybook stories (`*.stories.tsx`)

**Configuration**:
```javascript
// scripts/check-tokens-drift.mjs
const EXEMPT_FILES = [
  'final-override.css',
  '*.test.ts',
  '*.stories.tsx'
]
```

### Token API Reference

#### `getToken(path: string): any`

Access individual token values via dot notation.

```typescript
import { getToken } from '@morningai/shared-ui'

const primaryColor = getToken('color.primary.500')  // "#0ea5e9"
const spacingMd = getToken('space.md')              // "16px"
const fontBold = getToken('font.weight.bold')       // "700"
```

#### `getCSSVariables(): Record<string, string>`

Generate all CSS custom properties from tokens.

```typescript
import { getCSSVariables } from '@morningai/shared-ui'

const cssVars = getCSSVariables()
// Returns:
// {
//   '--color-primary-500': '#0ea5e9',
//   '--space-md': '16px',
//   '--font-weight-bold': '700',
//   ... (148+ variables)
// }
```

#### `applyDesignTokens(scope?: string | Element): HTMLElement`

Apply CSS variables to DOM element.

```typescript
import { applyDesignTokens } from '@morningai/shared-ui'

// Apply to document root (default)
applyDesignTokens()

// Apply to specific selector
applyDesignTokens('.theme-morning-ai')

// Apply to element reference
const container = document.getElementById('app')
applyDesignTokens(container)
```

**⚠️ API Change in PR #1173**: Default scope changed from `.theme-morning-ai` to `document.documentElement` for broader compatibility.

### Troubleshooting

#### Drift Check Failures

**Issue**: Hardcoded colors detected

**Solution**:
```css
/* Before (fails drift check) */
.button {
  background: #0ea5e9;
}

/* After (passes drift check) */
.button {
  background: var(--color-primary-500);
}
```

**Issue**: Direct token imports

**Solution**:
```typescript
// Before (fails drift check)
import tokens from '@morningai/shared-ui/tokens.json'
const color = tokens.color.primary[500]

// After (passes drift check)
import { getToken } from '@morningai/shared-ui'
const color = getToken('color.primary.500')
```

#### Token Not Found

**Issue**: `getToken()` returns `undefined`

**Solution**:
1. Verify token exists in `packages/shared-ui/src/tokens.json`
2. Check path syntax (use dots, not brackets): `'color.primary.500'` not `'color.primary[500]'`
3. Rebuild package: `cd packages/shared-ui && pnpm run build`

## Warning Mode Strategy

### Why Warning Mode?

All Phase 3 checks run in **non-blocking mode** during the initial 2-week period to:

1. **Collect baseline data** from real PRs
2. **Identify false positives** and adjust thresholds
3. **Validate check reliability** before enforcement
4. **Avoid blocking legitimate PRs** during calibration

### Warning Mode Implementation

All checks use `continue-on-error: true` in the workflow:

```yaml
- name: Run i18n coverage tests
  run: pnpm run test:i18n
  continue-on-error: true  # Non-blocking
```

### Exit Strategy

**Tracking Issue**: [Phase 3 Warning Mode Exit Strategy - Decision: 2025-11-21](https://github.com/RC918/morningai/issues/1172)

**Decision Timeline**:
- **Start**: 2025-11-07
- **Mid-point Review**: 2025-11-14 (1 week data)
- **Decision Meeting**: 2025-11-21
- **Implementation**: 2025-11-22+

**Success Criteria for Blocking Mode**:
- i18n coverage: ≥98% (based on 20+ PR data)
- A11y: Critical=0, Serious≤2
- Motion: P95<16.67ms, Dropped<1%
- VRT: Flake rate <3%

**Decision Options**:
- **Option A**: Enable blocking mode (all criteria met)
- **Option B**: Adjust thresholds and enable (data-driven adjustment)
- **Option C**: Extend observation period (insufficient data)
- **Option D**: Keep warning mode (checks unreliable)

## Troubleshooting

### i18n Coverage Failures

**Issue**: Coverage below 95%

**Solutions**:
1. Check for missing translations in `src/i18n/locales/zh-TW.json`
2. Verify key structure matches `en-US.json`
3. Review dynamic keys (may need ignore list)

**Issue**: Extra keys in secondary locale

**Solutions**:
1. Remove unused keys from `zh-TW.json`
2. Add missing keys to `en-US.json` if needed

### A11y Violations

**Issue**: Critical violations detected

**Solutions**:
1. Review `a11y-report.json` for specific violations
2. Fix WCAG issues (missing alt text, ARIA labels, etc.)
3. Run `pnpm run lint` to catch jsx-a11y issues early

### Motion Performance Issues

**Issue**: P95 > 16.67ms

**Solutions**:
1. Profile animations with Chrome DevTools
2. Reduce animation complexity
3. Use CSS transforms instead of layout properties
4. Consider hardware acceleration

### VRT Flakiness

**Issue**: High false positive rate

**Solutions**:
1. Update baseline: `pnpm run test:vrt -- --update-snapshots`
2. Increase threshold temporarily
3. Investigate dynamic content (timestamps, random data)
